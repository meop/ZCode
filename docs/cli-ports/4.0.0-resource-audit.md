# 4.0.0 active resource-retention audit

This follow-up records a fresh corrective-defect search requested after the initial port. The initial comparison
proved patch carry-forward and selected behavior, but did not establish that resource fixes required no expansion.
This audit found three additional retention defects. The fork therefore needs a larger corrective stack for 4.0.0.

Baseline: `802dcb9a8f7e807200ab02e6cbf71370e335c1bc` (the checked-in initial comparison), with executable source
`85a2c929b82f20204408938053628bb62aad2ad1` in `4.0.0-rc.1`. Upstream comparison: `v3.18.2` → `v4.0.0`, pinned
in [the port record](4.0.0.md). The follow-up targets `4.0.0-rc.2`; rc.1's tag is preserved.

## Review approach and findings

For each resource, trace allocation, owner, lifetime/size bound and retirement. Review old fixes against their causes,
and inspect newly reachable/current code for similar retention even when the old patch applies unchanged. The review
used source tracing and deterministic churn/lifecycle tests. It did not measure reclaimed megabytes or establish a
flat process-memory curve over hours.

## Remaining risks and follow-up boundaries

- The TUI still retains and mounts conversation history; transcript paging is not implemented. Tool-correlation and
  modified-file indexes also live with that history. Their size can grow with a long session even after these fixes.
  Silent eviction would change visible history/correlation behavior; a paging/persistence change needs its own design
  and user-facing acceptance cases.
- `adapters/src/mcp/index.ts` retains disconnected server records and generation state; dynamic removal still keeps
  historical records. This is a retention candidate for configuration-name churn, not covered by the empty resource
  subscription fix. Forgetting deconfigured records needs an explicit distinction from user-visible disconnect state
  and tests that preserve late-connection fencing; this audit does not claim to have solved it.
- Runtime task entries can retain completed outputs for TaskOutput/history. The registry has explicit remove paths,
  but this audit did not prove that every terminal task's history is eventually retired. Do not cap it blindly and
  break pending notifications, recovery or queryable results.
- No long authenticated workload, installed-plugin stress soak, native allocator profile or cross-platform memory
  comparison was performed. Deterministic state/handle regressions establish the properties above, not an overall
  memory ceiling or a measured reduction in process-tree PSS.

The active audit is bounded and repeatable, not a claim of exhaustive leak detection. These unresolved areas remain
visible for the next practical memory investigation; they must not disappear from the next port's comparison merely
because the current patch set applies cleanly.
